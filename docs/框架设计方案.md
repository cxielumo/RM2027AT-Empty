# RM2027AT 框架设计方案（逐文件）

版本：设计稿 v1，2026-09-27。本文描述目标架构；下方“当前落地状态”用于区分规划与已实现内容，不代表硬件或构建已验证。

当前落地状态：自维护源码按C99兼容方式编写。ADC、通信基础驱动、OS线程封装、PWM及DBUS基础已落地；`motor_tt`和`servo`尚未完成硬件标定，`motor_dji`仍为空表/待实现。硬件行为与完整构建均未经验证，本文中的验收项不能视为已通过。

## 1. 设计依据和边界

从当前PCB引脚重新设计，不受当前代码目录、接口或初始化方式约束。硬件依据见[功能引脚对应](功能引脚对应.md)，其连接核对范围和未确认项同样适用。功能参考 Lec4 的 `os / controller / can_motor / motor / pwm / servo`。

目标是交付一个可教学、可扩展的机器人控制基础工程：应用能够读取遥控器，控制六路板载直流驱动、两条CAN总线上的电机、六路舵机。业务算法和具体机器人动作由用户应用定义。

我们编写的代码保持C99兼容，项目默认C标准配置保持原样；采用AT32标准外设库、FreeRTOS；框架内部资源全部静态分配，仅Application允许按需动态分配。物理引脚集中定义，设备组件不直接访问寄存器。所有驱动输出默认处于未使能状态，初始化成功不自动启动执行器。首版不添加板上不存在的IMU、USB、蜂鸣器、业务按键和编码器功能。

设计中的周期、频率、缓冲区和栈大小是初始配置，需在实施时测量和调整。当前未执行构建或硬件验证。

## 2. 目录与单向依赖

按以下依赖关系组织：

```text
Application → Components → Bsp → ThirdParty + ATWP生成
     ↓             ↓
     └────── Algorithm ← Bsp（环形缓冲）
```

| 部分 | 职责 | 允许的直接依赖 |
|---|---|---|
| Application | 默认仅robot_main文件和用户任务入口，业务由用户填写 | Components、Algorithm；基础服务可直接使用Bsp的os/led/uart；非线程RTOS资源及静态线程创建直接使用FreeRTOS |
| Components | 遥控器、电机、舵机 | Bsp、Algorithm；非线程RTOS资源及静态线程创建直接使用FreeRTOS |
| Bsp | 硬件适配、OS封装、基础工具 | ThirdParty、ATWP生成；按需使用Algorithm中的环形缓冲 |
| ThirdParty | FreeRTOS内核和移植端口 | 芯片移植需要的ATWP配套CMSIS/设备头文件 |
| ATWP生成 | 启动、时钟、外设基础初始化、中断入口和配套厂商库 | 生成器配套库 |
| Algorithm | PID、斜坡、math_utils基础数学工具及静态环形缓冲等算法与数据结构 | C99标准库，不依赖上层和外设 |

设备控制仍遵循Application → Components → Bsp；Application可直接使用Bsp的os、led、uart基础服务，避免创建纯转发层，不直接使用芯片库接口。Components通过Bsp使用硬件和线程能力。os只封装App动态线程创建、调度、延时、时间查询与线程通知；Application、Components和Bsp的非线程资源由各自实现文件直接使用FreeRTOS队列、同步、临界区接口，静态线程创建也直接调用xTaskCreateStatic，这是依赖规则的显式例外。框架资源仍全部静态，仅App允许动态创建及分配。Application与Components均可直接包含Algorithm公共头文件并调用算法。Algorithm只依赖C99标准库，不依赖Bsp、RTOS、芯片库或上层模块。算法状态由调用者持有，每个控制对象使用独立实例；时间步长、输入和参数由调用者传入，不使用隐藏的全局实例池。Bsp不包含设备组件或Application头文件，不形成反向依赖。

目录布局：

```text
Application/robot_main.c
Components/Inc、Src
Bsp/Inc、Src
Algorithm/Inc、Src
ThirdParty/FreeRTOS/Source、Config
RM2027AT.ATWP
project/inc、project/src、project/MDK_V5/
libraries/
startup_at32f423.s
AT32F423xC_FLASH.ld
cmake/at32_workbench/
```

“ATWP生成”是文件归属，沿用生成器目录布局。main与IRQ是启动/中断的接入边界：main用户区仅调用应用启动入口，IRQ用户区仅转发Bsp或RTOS处理函数。这两个接入点允许调用上层入口，不允许在生成代码中实现业务逻辑；它们是依赖规则的显式例外。

物理引脚与MUX由ATWP配置管理，Bsp资源表引用并核对。根目录构建和docs是工程配套文件，不参与功能层依赖。

## 3. 硬件资源分配

### 3.1 六路板载驱动

电机按用户指定顺序编号：1=CN9、2=CN5、3=CN6、4=CN7、5=CN8、6=CN10。公共设备ID为`MOTOR_TT_1`至`MOTOR_TT_6`，枚举值为0至5，`LAST_MOTOR_TT`为数量上界，内部数组直接以枚举值索引。连接器名称保留在板级映射表中。

| 设备ID | 接口/芯片 | IN1 | IN2 | 定时器组 | 默认用途 |
|---|---|---|---|---|---|
| MOTOR_TT_1 | CN9/U8 | PB8 TMR4_CH3 | PB9 TMR4_CH4 | TMR4 | 直流电机 |
| MOTOR_TT_2 | CN5/U9 | PB7 TMR4_CH2 | PB6 TMR4_CH1 | TMR4 | 直流电机 |
| MOTOR_TT_3 | CN6/U10 | PB5 TMR3_CH2 | PB4 TMR3_CH1 | TMR3 | 直流电机 |
| MOTOR_TT_4 | CN7/U11 | PA10 TMR1_CH3 | PA9 TMR1_CH2 | TMR1 | 直流电机 |
| MOTOR_TT_5 | CN8/U12 | PB15 TMR12_CH2 | PB14 TMR12_CH1 | TMR12 | 直流电机 |
| MOTOR_TT_6 | CN10/U13 | PB10 TMR2_CH3 | PB2 TMR2_CH4 | TMR2 | 直流电机 |

MOTOR_TT_3（CN6/TMR3）与MOTOR_TT_6（CN10/TMR2）采用50Hz，其余四路电机采用20kHz。两路低频电机的转矩脉动、噪声、电流和温升须实测确认。`motor_tt_set_duty()`接收[-1,1]，这是开环输出比例，不是实际转速。CN10的输出接线顺序单独记录在映射表，正方向通过每设备`invert`标志定义。CN8.3没有已确认反馈连接，不提供伪造的编码器接口。

RZ7889输入真值表未在本次硬件解析中确认，因此实施前必须确定停机电平、制动/滑行行为、换向要求。设计不预先把双低解释为某种停机模式；这些规则集中在`motor_tt.c`的私有函数。

### 3.2 六路舵机与六路电机：TMR2/TMR3共用50Hz

TMR2、TMR3降至50Hz（20ms周期），供各自的电机和舵机共享；TMR13、TMR14保持舵机50Hz。TMR1、TMR4、TMR12使用电机20kHz。各通道独立设置比较值，全部采用原引脚的硬件PWM输出；不切换到TMR9互补输出。不同定时器相位默认无需同步。

| 定时器 | 频率 | 对应设备 |
|---|---|---|
| TMR1 | 20kHz | MOTOR_TT_4 / CN7 |
| TMR2 | 50Hz | MOTOR_TT_6 / CN10、SERVO_5、SERVO_6 |
| TMR3 | 50Hz | MOTOR_TT_3 / CN6、SERVO_1、SERVO_2 |
| TMR4 | 20kHz | MOTOR_TT_1 / CN9、MOTOR_TT_2 / CN5 |
| TMR12 | 20kHz | MOTOR_TT_5 / CN8 |
| TMR13 | 50Hz | SERVO_4 |
| TMR14 | 50Hz | SERVO_3 |

| 舵机ID | 接口 | 引脚 | 硬件PWM通道 | 同组电机 |
|---|---|---|---|---|
| SERVO_1 | H1.1 | PB1 | TMR3_CH4 | MOTOR_TT_3/CN6 |
| SERVO_2 | H1.2 | PB0 | TMR3_CH3 | MOTOR_TT_3/CN6 |
| SERVO_3 | H1.3 | PA7 | TMR14_CH1 | 无 |
| SERVO_4 | H1.4 | PA6 | TMR13_CH1 | 无 |
| SERVO_5 | H1.5 | PA1 | TMR2_CH2 | MOTOR_TT_6/CN10 |
| SERVO_6 | H1.6 | PA0 | TMR2_CH1 | MOTOR_TT_6/CN10 |

编号SERVO_1～6取值1～6，0无效。H1.7/8保留USART6 RX/TX。TMR2全部四通道设为输出，取消原CH1输入捕获用途。TMR3全部四通道输出；CN9/MOTOR_1和CN5/MOTOR_2共享TMR4。

#### 计数与占空比

50Hz组目标计数频率1MHz，周期计数N=20000，周期寄存器对应N−1=19999。20kHz组选择更高的计数频率以保留占空比分辨率，按`N = f_count / 20000`计算周期；不能照搬1MHz计数而仅剩50个占空比等级。预分频值由各定时器的实际输入时钟计算，不能直接假设等于APB时钟；若无法精确分频，记录实际计数频率并用它换算。

边沿对齐、有效高电平PWM模式下，比较值取`round(duty * N)`。舵机通过脉宽换算`duty = pulse_us / 20000`；例如1000µs=5%、1500µs=7.5%、2000µs=10%，只是计算示例，不替代具体舵机标定。电机命令[-1,1]的绝对值转换成占空比，符号交给RZ7889驱动映射方向。

每个通道可以有不同占空比，但同一定时器全部通道共用周期。改变占空比不会改变PWM基础频率，不能由50Hz占空比设置获得20kHz电机PWM。0%和100%的比较寄存器边界及实际输出电平必须验证。

#### 更新与关闭

周期和比较值启用适当的预装载，组频率只在初始化阶段设置。运行期更新比较值，在硬件更新边界生效，不为单个舵机修改组周期。1kHz控制循环可持续更新目标，但TMR2/3/13/14的50Hz PWM实际生效间隔仍为20ms，最新值可能覆盖尚未输出的旧值。

桥驱动双输入需在同一个更新边界提交。仅启用CCR预装载不足以保证两次写入间不会跨越更新边界，pwm须采用芯片支持的短时更新抑制/统一提交机制，并验证不会重置其他通道的相位。禁止为刷新某个通道而随意生成影响全组的更新事件。

关闭单通道只作用于该通道或对应桥输入对，不能停止共用计数器或关闭全组主输出而误伤其他设备。故障关闭全部输出可统一处理。关闭后的引脚电平和桥驱动停机模式按硬件确认，不能仅把“停止计数”视为拉低输出。重新使能应在完整周期边界应用有效比较值。

#### 方案取舍与验收

此分组使六路电机和六路舵机可以同时使用现有硬件PWM通道。仅MOTOR_3、MOTOR_6承受50Hz调制，可能出现明显转矩脉动、噪声和较大的瞬时电流；这两路不预先承诺与其余四路20kHz电机具有同等控制效果。实测无法满足负载时，需要重新评估频率或硬件方案。

H2经F1接+5V，H3接地；六舵机的总供电能力需按实际负载确认。波形验收覆盖全部通道的周期、脉宽、0/100%边界、双输入更新一致性，以及关闭单通道不影响同组其它通道。

### 4.4 Bsp精简原则

Bsp仅保留板级初始化和实际外设封装。固定引脚、设备资源和定时器频率集中在bsp.c的静态配置表，移除运行时资源分配/profile系统。组件只选择既定设备ID，初始化检查ID和参数是否合法，不动态更换引脚或重新分配定时器。

时钟初始化与IRQ入口由ATWP生成；Bsp驱动直接查询厂商时钟信息，IRQ处理函数在各驱动头文件声明。故障处理合入bsp.c，RTOS hooks合入os.c。不可恢复错误直接调用panic()，可恢复操作错误忽略；简单字节序转换留在协议文件私有static inline函数中，超时由使用方按无符号时间差判断，不额外封装os_elapsed或拆文件。

Bsp默认不创建统一I/O线程。某个驱动确实需要后台处理时，可在自己的.c文件内创建私有静态线程，栈、任务控制块、队列和同步对象全部静态；线程预算按新增情况更新。Algorithm继续独立提供ringBuffer和math_utils。

### 4.5 Algorithm：独立纯算法

本目录可独立编译，也可直接用于主机测试。Application和Components按需链接；Bsp可直接使用本目录的环形缓冲，仍不承担控制算法转发。

| 文件 | 精确职责/接口 |
|---|---|
| Algorithm/Inc/ringBuffer.h | 单生产者/单消费者字节环形缓冲接口 |
| Algorithm/Src/ringBuffer.c | 调用者提供静态存储区，固定容量、满/空处理和溢出计数；内部不申请内存，不隐式覆盖旧数据 |
| Algorithm/Inc/pid.h | PID状态、参数、`pid_reset()`、`pid_step(..., dt_s)` |
| Algorithm/Src/pid.c | 输出限制、积分限制/抗饱和、有限数输入处理 |
| Algorithm/Inc/ramp.h | 指令变化率限制接口，单位每秒 |
| Algorithm/Src/ramp.c | 使用显式dt的斜坡计算 |
| Algorithm/Inc/math_utils.h | static inline定义clampf/deadzone，直接返回计算值；处理非法区间、宽度及非有限输入；定义DEG2RAD/RAD2DEG转换宏；无对应.c文件 |

`math_utils`使用C99，不依赖硬件、RTOS或动态内存；函数不持有隐藏状态。PID和斜坡继续保留独立文件，通用数学计算复用math_utils。

环形缓冲只实现数据结构，不依赖RTOS、外设或中断。Bsp/Components在各自模块中静态定义缓冲对象和存储区，再传入初始化函数。任务与ISR并发所需的临界区、内存可见性和生产者/消费者约束由使用方负责，不将volatile视为完整同步机制。

PID和斜坡用于应用选择的闭环，不把无反馈的板载直流电机包装成速度闭环。首版不引入无传感器来源的AHRS模块。

### 4.6 Bsp：精简文件清单

共8组.h/.c文件，另有仅定义共享引脚类型的gpio.h。下列每个路径都是独立文件，无额外board、profile、clock、irq、fault、output、io_task或os_hooks文件。

| 文件 | 精确职责/接口 |
|---|---|
| Bsp/Inc/bsp.h | 故障类型、bsp_init()和panic()声明；设备ID和资源描述归对应模块头文件；仅bsp模块入口使用bsp命名，不给其它模块加层名前缀 |
| Bsp/Src/bsp.c | 固定引脚/外设/频率静态表；依次初始化驱动状态；集中处理必要故障，调用pwm关闭本地执行器；不重复执行ATWP基础初始化 |
| Bsp/Inc/gpio.h | 仅定义gpio_port_t和pin_desc_t共享类型；无对应.c文件，不增加GPIO服务层 |
| Bsp/Inc/os.h | 仅封装App动态线程创建、调度、延时/周期等待、时间查询和线程通知；App可动态创建/删除线程；栈单位word |
| Bsp/Src/os.c | 线程接口封装、Idle静态内存、栈溢出hook和断言转panic；不使用隐藏任务槽池 |
| Bsp/Inc/pwm.h | 固定通道ID；初始化、占空比设置、成对设置、单通道/成对/全部关闭；设置即输出，无独立enable和时序查询 |
| Bsp/Src/pwm.c | 使用bsp.c映射与固定组频率，查询实际时钟、计算比较值、处理预装载/同步提交/主输出；运行期不开放任意改频 |
| Bsp/Inc/can.h | 双CAN初始化、非阻塞单帧发送/接收及IRQ入口；不提供任务绑定和状态查询 |
| Bsp/Src/can.c | 每总线静态RX队列、固定滤波和硬件TX邮箱；邮箱满时忽略发送请求，无软件TX队列；错误恢复留在驱动内，不解设备协议 |
| Bsp/Inc/uart.h | 串口收发、帧间隔/错误事件及IRQ处理函数声明 |
| Bsp/Src/uart.c | USART6循环DMA接收、静态缓冲及空闲事件；USART1收发/TX DMA暂缓；按需使用Algorithm/ringBuffer |
| Bsp/Inc/adc.h | 原始ADC值、采样状态及采样接口 |
| Bsp/Src/adc.c | ADC1_IN2采样、校准和超时，不含电压换算 |
| Bsp/Inc/led.h | led_set(led_id_t id, bool on)；LED_1=1、LED_2=2、LED_3=3，0无效 |

bsp.c只持有映射表和初始化顺序，不实现各外设的收发逻辑；表通过各驱动头文件声明的只读描述接口提供给驱动（实现在bsp.c）；bsp.h不反向包含驱动头文件，不能让驱动调用bsp_init形成初始化递归。故障关闭路径不依赖RTOS锁，也不等待通信发送完成。

`pwm`的组件接口只使用通道ID；定时器组与资源描述仅供板级映射接入。舵机脉宽在servo.c换算为占空比，pwm不提供脉宽接口。同组设备设置不同占空比是允许的；运行期请求改频不属于公共接口。桥驱动两输入的切换按芯片要求成对更新，不能任意顺序连续写造成瞬时错误状态。

USART6接收采用DMA1 Channel1循环DMA（DMAMUX USART6_RX）及IDLE/半满/全满事件，使用静态128字节DMA缓冲并复制到帧槽；旧的逐字节轮询接收路径必须停用。USART1收发与TX DMA暂缓，不要求配置DMA1 Channel2。DMA和USART6中断抢占优先级均为5、子优先级0；缓冲就绪后再启用接收。

### 4.7 Components：精简为五组文件

配置、协议解析、超时和私有静态线程归所属组件管理，不建立统一配置中心、通信任务、监测任务、日志框架、系统服务转发或输出管理模块。共有5组.h/.c文件。

| 文件 | 精确职责/接口 |
|---|---|
| Components/Inc/dbus.h | 遥控器初始化、输入快照和在线状态接口；摇杆/开关/鼠标/按键/时间戳结构 |
| Components/Src/dbus.c | 静态接收线程、18字节协议解包、合法性检查、死区、超时和一致快照；滚轮保留原始字段，型号确认后解释 |
| Components/Inc/motor_dji.h | CAN电机ID/型号配置类型、反馈快照、原始电流目标和启停接口 |
| Components/Src/motor_dji.c | 静态设备表和服务线程；双总线反馈解析、角度累计、成组打包发送、设备超时；内部包含协议细节 |
| Components/Inc/motor_tt.h | motor_tt_set_duty(id,ratio)、motor_tt_stop(id)、motor_tt_enable(id)；在此定义motor_id_t和编号MOTOR_1～6 |
| Components/Src/motor_tt.c | 电机方向静态表、限幅和使能状态；私有函数实现RZ7889输入真值表及双通道更新；无反馈时不报告转速，默认不开线程 |
| Components/Inc/servo.h | servo_set_pulse_us()、servo_set_angle_deg()、servo_enable()；在此定义servo_id_t和编号SERVO_1～6 |
| Components/Src/servo.c | 六路标定静态表、角度/脉宽转换、输出启停；调用pwm，默认不开线程 |

每个组件自己的.h声明可配置参数和公共接口，默认配置表放对应.c。物理引脚只由Bsp维护；组件保存设备型号、方向、脉宽标定等语义配置。任务优先级、栈、周期和超时常量集中在对应.c顶部，不增加components_config文件。

dbus线程只处理遥控器；motor_dji线程汇总双CAN收发，不按每台电机各建线程。静态栈、控制块、队列和同步对象全部由各自.c持有。

CAN协议类型决定原始电流限值、反馈ID及命令槽。配置时检查同总线重复反馈ID/命令槽；不同总线分别维护命令缓冲。Lec4的0x200/0x1FF/0x2FF仅作为参考，未配置槽填零，不假设任意12个ID可无冲突混接。接收只接受支持的帧型和长度。

多圈角度首帧建立基准，后续折回[-4096,4095]累计；超过半圈/采样周期有歧义，掉线后重建基准并标记连续性失效。角度与字节序处理作为motor_dji.c私有函数，通用数学复用Algorithm。

设备自身反馈/命令超时与停机规则在所属组件中实现。遥控器掉线是否关闭某台电机属于robot_main业务决策，不让dbus直接控制其它组件。motor_tt/servo默认关闭，显式使能后接受命令；需要周期性命令超时服务时可在所属.c增加静态线程并计入预算。不开后台线程时不承诺无人调用也能定时发现超时。

六路舵机使用50Hz硬件PWM，脉宽按每台舵机标定换算，不能直接照搬Lec4固定占空比。组件处理NaN、无限值和越界输入，不将非法数据写入寄存器。独立日志功能留给用户，基础输出直接使用uart接口。

### 4.8 Application：仅提供robot_main

默认仅一个文件：`Application/robot_main.c`，仅定义一个用户进程（FreeRTOS任务）入口函数`void robot_main(void *args)`。不预设app、robot_step、控制任务、业务状态机或其它应用文件；用户后续按实际业务自行扩展。

```c
#include "os.h"

void robot_main(void *args)
{
    (void)args;

    /* 用户的一次性初始化。框架及组件已在调度前完成初始化。 */
    for (;;) {
        /* 用户控制逻辑：读取组件数据，调用电机/舵机接口。 */
        os_delay(1U);
    }
}
```

`os_delay()`由Bsp/os提供。默认循环只延时，不自动驱动执行器，也不固定用户最终控制周期。需要固定周期控制时，用户可使用os提供的绝对周期等待接口。

`project/src/main.c`用户代码区写`extern void robot_main(void *args);`，并静态定义robot_main的栈和任务控制块。main直接调用FreeRTOS的xTaskCreateStatic传入robot_main，再调用调度器启动接口。Application无需额外头文件；Components不引用robot_main名称。该入口函数不能返回。

用户可以直接调用Components组件接口及独立Algorithm。Lec4调用迁移示例：`Motor_SendCommand(T1,x)`对应`motor_tt_set_duty(MOTOR_TT_4,x)`；舵机使用SERVO_1～6；遥控器读取一致快照。

## 5. 分层静态线程与共享数据规则

Components和Bsp均可按需创建静态线程处理自己的数据。线程是模块内部实现，模块公共API不要求用户在robot_main中反复调用poll。无需后台工作的模块（如简单LED、纯算法）不创建线程，也不要求每个文件各开一条线程。

Components和Bsp的线程入口、静态栈、任务控制块、队列存储区及控制块、同步对象由所属模块的.c文件持有；初始化阶段和运行阶段都禁止为框架内部资源动态分配，也不隐式使用共享任务槽池。模块初始化函数负责创建和检查结果，重复初始化不重复建线程。线程调用方向仍遵循分层：Bsp处理硬件事件/原始数据，Components处理设备协议/状态，Application处理用户业务。Algorithm保持纯计算且不开线程。

| 执行者 | 所属文件 | 初始优先级/周期 | 栈初始预算 | 工作 |
|---|---|---|---|---|
| dbus_task | Components/Src/dbus.c | 5，事件驱动，带超时等待 | 384 words | 遥控器解包、在线状态与快照 |
| motor_dji_task | Components/Src/motor_dji.c | 5，默认1ms周期，有界读取两总线RX队列 | 768 words | 双CAN电机反馈与成组指令 |
| robot_main | Application/robot_main.c | 4，默认循环延时1ms | 768 words | 用户进程入口，实际业务周期由用户决定 |
| Idle | FreeRTOS | 0 | 128 words | 系统空闲 |

这是初始线程划分，允许组件按实际需要拆出私有线程；新增线程时必须同步预算并明确其唯一写入的数据。接收原始数据的搬运仍由ISR完成，按需创建的驱动线程不替代及时接收中断。UART使用可等待帧队列；CAN由motor_dji任务每1ms有界读取ISR已经填充的接收队列，不直接轮询硬件单帧寄存器。

Bsp不引用Components函数名称或头文件。UART使用可等待帧队列，CAN只提供非阻塞接收，不注册上层任务；协议解析在Components线程执行。组件通过API接收用户命令，内部线程可以作为硬件提交的唯一执行者。

优先级数字越大越高。组件通信线程和按需增加的驱动线程每轮限定处理帧数/时间预算；持续洪泛时必须真正阻塞让出时间（仅taskYIELD不能让低优先级任务运行），不能无限排空导致控制任务饥饿。需要周期控制时，robot_main使用绝对周期等待，dt使用实际时间差；框架不强制用户业务周期。

通信中断只搬运数据、清标志、计数并发通知。舵机边沿由硬件PWM自动生成，不需要边沿定时中断。所有调用RTOS FromISR API的中断，其优先级必须满足MAX_SYSCALL约束；具体NVIC数值在核实芯片优先级位数后集中定义。中断内禁止printf、协议解析、动态内存和等待发送。

遥控器接收采用双帧缓冲，ISR提交长度和错误标记后不再修改该帧；不能让解析线程读取仍被覆盖的DMA/ISR缓冲。没有有效CRC的协议只能做结构与范围检查，不能声称可靠识别所有损坏帧。控制器在线时间只在完整合法帧后刷新。

CAN每总线初始接收队列32帧；队列满计数并丢弃新帧。motor_dji保存每组最新目标，每轮重新打包后直接尝试硬件邮箱；BUSY时下一轮使用新目标，不建立软件TX队列。总线由收发参数指定，帧携带标准/扩展及数据/远程类型；组件拒绝不支持帧型与长度。

反馈快照通过短临界区或短互斥保护完整复制；不能依赖volatile保证结构一致。遥控器与CAN反馈的写者各自唯一。robot_main提交业务目标；每项执行器状态和底层输出明确一个写入者。由组件线程提交CAN命令时，用户只更新命令缓冲，CAN驱动统一串行管理邮箱发送；直接同步的PWM接口则由其指定调用线程提交。不得让用户线程和后台线程同时修改同一输出。故障入口允许直接关闭本地输出并撤销旧命令。

## 6. 生命周期和输出语义

1. ATWP生成的main完成时钟和基础外设初始化。
2. main用户区调用`bsp_init()`，建立驱动缓冲和同步对象；驱动按需创建私有静态线程。缓冲就绪前不使能业务接收中断，输出保持关闭。
3. main用户区直接依次调用`motor_tt_init()`、`servo_init()`、`dbus_init()`初始化组件及其私有静态线程；不再调用bsp_init。
4. main使用本文件静态持有的栈和任务控制块，直接通过FreeRTOS的`xTaskCreateStatic()`创建`robot_main`任务，入口签名为`void robot_main(void *args)`；创建函数直接返回任务句柄，失败返回`NULL`，main检查句柄后再启动调度器。
5. main创建任务失败时直接panic；下层初始化遇到致命错误直接panic，然后统一启动调度器。调度器若意外返回，也进入故障处理。各下层模块不得自行启动调度器。
6. robot_main执行用户初始化并进入循环，调用组件接口处理业务。

启动关系：

```text
main（ATWP用户代码区）
  ├─ ATWP生成的基础初始化
  ├─ bsp_init()
  ├─ motor_tt_init() → servo_init() → dbus_init()
  ├─ 静态创建robot_main任务
  └─ 启动调度器
```

main是明确的装配点，可以同时引用Bsp、Components和robot_main声明。静态任务存储放在main文件作用域的用户变量区，调用放在用户代码区，确保ATWP重新生成时保留。移除components_start接口；无需另建启动协调模块。

默认遥控器和CAN反馈超时设计值为100ms，可按设备调整。舵机超时后的动作由设备配置决定，默认关闭脉冲；CAN断线时不能保证零命令抵达远端。框架不预设BOOT/DISARMED/ACTIVE等机器人业务状态机，不强制独立control_task，也不设置尚未约定周期的用户任务超期阈值。

## 7. 内存和构建约束

### 内存分配边界

- Components、Bsp的任务栈、任务控制块、队列数据区/控制块、信号量、互斥锁、事件组及长期缓冲全部静态持有，使用对应Static创建接口；启动时分配也不例外。
- Algorithm的状态和工作区由调用者提供，算法内部不申请堆内存。框架所使用的RTOS系统对象（如Idle，若启用软件定时器则包括其任务栈/控制块）也走静态分配。
- 仅Application可按需动态创建自己的任务、队列、同步对象或申请业务内存；允许动态不等于必须动态。默认robot_main的栈和任务控制块由main文件作用域静态提供。
- Application通过Bsp/os动态线程接口创建自己的线程；动态队列、同步对象与业务内存直接使用FreeRTOS创建/删除及pvPortMalloc/vPortFree。资源归Application所有，Components、Bsp内部不得动态分配。os不封装队列、互斥、临界区和内存接口。
- FreeRTOS配置`configSUPPORT_STATIC_ALLOCATION=1`、`configSUPPORT_DYNAMIC_ALLOCATION=1`。仅链接一个堆实现，首版选择`ThirdParty/FreeRTOS/Source/portable/MemMang/heap_4.c`；其固定堆区容量由RAM预算确定，不能与静态对象重复计算。
- App内存接口采用同一FreeRTOS堆；普通业务内存使用成对申请/释放，任务/队列等RTOS对象使用对应删除接口，不能直接free句柄。动态任务栈由RTOS管理，删除后回收时机遵循RTOS规则。调用方必须处理创建失败，并在删除前停止所有引用者。
- C库堆与FreeRTOS堆不混用。中断上下文禁止动态分配。文档中的“静态线程”约束针对框架内部线程；App新增线程可自行选择静态或动态。


C99是我们编写代码的兼容性约束，不是项目编译标准的修改要求。Application、Components、Bsp、Algorithm及自维护配置、测试代码和用户代码区新增内容均使用C99兼容语法。保留CMake、Keil及ATWP生成工程默认的C标准设置，不为此改写CMAKE_C_STANDARD、编译器标准选项或生成器检查。第三方和生成代码沿用各自要求；即使项目默认以C11或更新标准编译，我们的代码也不依赖新增语言特性。

不使用C11的`_Static_assert`、`_Atomic`、`_Generic`和匿名结构/联合等特性。编译期断言采用带唯一名称的typedef数组方式；并发同步采用RTOS临界区、互斥或经过定义的单生产者/单消费者协议。头文件内的小函数使用`static inline`，避免不同编译器对外部inline定义的差异。芯片库、CMSIS和RTOS端口所需的汇编、对齐、弱符号等编译器扩展限定在依赖和平台适配层，不能据此宣称这些底层文件是纯标准C99；实施时分别检查GCC与Keil兼容性。

默认线程栈初始合计2048 words（约8KiB，按32位word）；按需增加的驱动线程另行计入；另计RTOS任务对象、CAN队列、UART缓冲及应用数据。UART初始预算：USART6 DMA循环缓冲128字节及双64字节帧缓冲；USART1暂缓，不计入TX缓冲；还须计入供Application动态分配的FreeRTOS堆、必要的C库堆保留和中断栈；实际RAM总量以芯片资料和链接map核对。开启栈水位和溢出检测，不把预算当作验证结果。

ATWP配套libraries、ThirdParty/FreeRTOS作为固定版本依赖保留许可证。GCC与Keil只选择各自一个启动文件和一个RTOS端口，不能混用。CMake和Keil源文件清单必须一致；新增模块时同时更新显式清单。

ATWP负责生成基础外设代码；main和中断接入保留在用户代码区。重新生成后检查这些接入、自维护代码的C99兼容性、RTOS端口、源文件清单和输出初始状态。Application、Components、Bsp、Algorithm不放进生成目录。生成构建清单通过自维护cmake/sources.cmake接入Application、Components、Bsp和Algorithm源码；生成器会覆盖的字段需在再生成流程中复核。自维护Bsp文件、类型、函数和任务名不加层名前缀，采用gpio、pwm、can、uart等模块名；公共符号须避免与厂商库重名，发生冲突时使用体现操作语义的名称。void操作API忽略可恢复错误，有结果的API用int返回（0成功、-1失败），仅isXxx/hasXxx谓词用bool；初始化致命错误调用panic()；数据单位写入名称或注释（ms、us、deg、raw_current、duty）。
